# Google authentication transition

Status as of September 10, 2026: Google now grants new Google Ads API access through a Google Cloud project. New users enable the API and request the appropriate access level from the project's Google Ads API Overview page. Do not apply for a new developer token through the retired Google Ads API Center. See Google's [developer-token retirement notice](https://developers.google.com/google-ads/api/docs/api-policy/developer-token), [Cloud project setup](https://developers.google.com/google-ads/api/docs/oauth/cloud-project), and [access levels](https://developers.google.com/google-ads/api/docs/api-policy/access-levels).

This project now declares `google-ads>=32.0.0,<33`. Version 32 removes developer-token validation and the old limited-pilot cloud-organization switch. An isolated offline environment resolved and installed 32.0.0, and source-level regression checks cover its tokenless service-account selection while retaining the older user-authorization profile. A bounded September 10, 2026 check also refreshed one existing user-authorization profile and verified account discovery plus startup prerequisites and health for one selected advertiser; see [release readiness](release-readiness.md) for the exact limits. This does not prove key creation, first-time sign-in, recovery, an assistant client connection, every provider operation, or stable-release readiness. The old pilot switch is not a supported bypass, and users must not invent a developer token.

The setup guide recommends a service account and retains the older Desktop user profile for someone who already has those credentials. The connected fresh-user journey remains unproven.

Google recommends service accounts when possible. A service account is an app-owned identity that receives access to the relevant Google Ads accounts. The profile uses `json_key_file_path`; `impersonated_email` is optional, and `developer_token` is optional for backward compatibility. Google documents [service-account setup](https://developers.google.com/google-ads/api/docs/oauth/service-accounts) and [private-key creation](https://docs.cloud.google.com/iam/docs/keys-create-delete). If policy blocks key creation, use an administrator-approved route or the Desktop fallback rather than weakening organization policy. No service account, key, account access, startup, or live request was created or tested.

Google also retains Desktop user sign-in as a fallback for a person authorizing an installed application. Its current guidance covers [single-user authentication](https://developers.google.com/google-ads/api/docs/oauth/single-user-authentication), [Desktop client creation](https://developers.google.com/workspace/guides/create-credentials), and [OAuth consent configuration](https://developers.google.com/workspace/guides/configure-oauth-consent). Desktop loopback sign-in is documented for [native apps](https://developers.google.com/identity/protocols/oauth2/native-app); the retired manual copy-and-paste flow is not the path to build. This project includes a packaged Desktop helper that can create or replace one private profile and has passed synthetic offline tests using simulated sign-in; use the [setup guide](setup.md) for the exact command. A bounded September 11, 2026 check completed real Desktop sign-in/private save and loaded the new profile for read-only account health through an MCP client (OpenAI Codex). Explicit profile replacement and post-restart health also passed; recovery after token revocation remains unverified.

Google no longer requires a manager account merely to register for API access. This server still requires `login_customer_id` and checks at startup that every authorized advertising customer is below that login manager. Those account restrictions are server safety rules and remain in force regardless of Google's registration change.

New Cloud projects begin with test access. Production use requires the appropriate production access upgrade. Access levels can also limit services: Google's Explorer access restricts planning services, including `KeywordPlanIdeaService`, so a successful basic read does not prove that every planning tool is available. Confirm the required access level before relying on the server's full tool set.

Use the [setup guide](setup.md) for exact private profile and Model Context Protocol client placement. Desktop sign-in/private save and a health-only MCP client connection have bounded connected evidence. From-zero Cloud registration, service-account setup, revoked-token recovery and broader operation-specific provider behavior still require separate verification.
