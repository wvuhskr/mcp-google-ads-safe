## Labels and common boundaries

Current evidence uses these exact tiers:

- **Offline synthetic**: local tests or serialized version 25 messages with fake
  account responses. This is request-shape and safety-logic evidence only.
- **Historical live read**: a dated provider read was recorded for that exact
  operation or query revision. It is not proof for changed source or another row.
- **Historical exact-payload validation**: Google accepted `validate_only=true`
  for the exact mutation payload; nothing was saved.
- **Historical applied plus independent readback**: the exact change was applied
  and separately read back at the time stated in the retained record.
- **Unavailable**: no applicable provider evidence was found.

Future capability labels are provisional planning labels. **Candidate** means the
operation might be provable in a safely isolated account if an eligible account
existed. Test-account provisioning was abandoned on September 4, 2026 and must not
be retried. The active future strategy is an individually approved real-account
probe. **Needs live** means saved state, provider-generated data, policy, serving,
or account eligibility can only be observed against a provider account. **Local
only** means no provider capability exists to prove. None of these labels grants
permission to make a call.

Every provider read requires approved credentials, a fresh readable account and
complete pagination. Every draft requires writes enabled, read and write
allowlists, exact current-state reads, applicable feature opt-ins, a separate
`confirm_and_apply`, and individual approval before a live write. Validation-only
support means the internal dispatcher can send the same compiled payload with
`validate_only=true`; it is not a public tool argument and does not prove saved
state. Refusals below are representative trust-boundary checks, not exhaustive.
